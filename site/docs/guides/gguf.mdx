# Run GGUF models

For optimal performance and memory consumption, use prepared OpenVINO IR models from [OpenVINO on Hugging Face](https://huggingface.co/OpenVINO) whenever a suitable model is available. These models are created by exporting and compressing Hugging Face models with [Optimum Intel](https://huggingface.co/docs/optimum-intel/openvino/export). If no prepared IR is available, you can use the same export path to create one from the source model.

Use the GGUF frontend when your model is available only in GGUF format or you need to run an existing GGUF file directly.

OpenVINO GenAI can load a local `.gguf` file directly, including its tokenizer metadata. No Optimum export is required. `ENABLE_GGUF` is enabled by default in GenAI CMake. Use a compatible OpenVINO build that includes the GGUF frontend.

The default `GGUF_READER="LEGACY"` supports the `llama`, `qwen2`, and `qwen3` architectures. Select `GGUF_READER="FRONTEND"` explicitly to use the OpenVINO GGUF frontend, which supports more architectures and is expected to provide better model quality through more complete handling of GGUF metadata.

:::warning Preview feature
The GGUF frontend is in preview. Architecture, quantization, tokenizer, and attention-backend support depend on the OpenVINO version. Generated output can differ from other runtimes. If the default legacy reader fails, GenAI includes a suggestion to try the frontend in the error message; retry by selecting it explicitly.
:::

Prefer models quantized in `Q4_0` or `Q8_0` format for better performance and accuracy. Their quantization layouts are closest to those used by OpenVINO.

## Generate text

Replace `model.gguf` with the path to your downloaded model. For a base model without a chat template, set `apply_chat_template=False` in Python or `config.apply_chat_template = false` in C++.

<LanguageTabs>
    <TabItemPython>
        ```python
        import openvino_genai as genai

        pipe = genai.LLMPipeline("model.gguf", "CPU", GGUF_READER="FRONTEND")
        print(pipe.generate("Explain why the sky is blue.", max_new_tokens=64))
        ```
    </TabItemPython>
    <TabItemCpp>
        ```cpp
        #include <iostream>
        #include <openvino/genai/gguf.hpp>
        #include <openvino/genai/llm_pipeline.hpp>

        int main() {
            ov::genai::LLMPipeline pipe(
                "model.gguf", "CPU", ov::genai::gguf_reader("FRONTEND"));
            ov::genai::GenerationConfig config;
            config.max_new_tokens = 64;
            std::cout << pipe.generate("Explain why the sky is blue.", config);
        }
        ```
    </TabItemCpp>
</LanguageTabs>

## Use the tokenizer and stream a chat

The pipeline constructs its tokenizer from the frontend's model metadata. You can also construct `genai.GGUFTokenizer("model.gguf")` independently, without exporting tokenizer IR files. In C++, include `<openvino/genai/gguf.hpp>` and use `ov::genai::GGUFTokenizer`. The existing `Tokenizer("model.gguf")` path also remains supported.

For GGUF BPE tokenizers, `skip_special_tokens=True` removes control tokens but preserves user-defined tokens, such as Qwen reasoning and tool-call delimiters, based on the token type stored in the GGUF file. Unlike llama.cpp, GenAI does not additionally treat known end-of-generation tokens stored as user-defined, such as Gemma 4 `<|tool_response>`, as control tokens. GGUF files do not store the original Hugging Face `special` flags, so the result can differ from a tokenizer exported with Optimum Intel. For identical behavior, pass a tokenizer exported for the same model to the pipeline: `genai.LLMPipeline("model.gguf", genai.Tokenizer("tokenizer_dir"), "CPU", GGUF_READER="FRONTEND")`.

```python
import openvino_genai as genai

pipe = genai.LLMPipeline("model.gguf", "CPU", GGUF_READER="FRONTEND")
tokenizer = pipe.get_tokenizer()
encoded = tokenizer.encode("Hello", add_special_tokens=False)
print(tokenizer.decode(encoded.input_ids))

history = genai.ChatHistory()
history.append({"role": "user", "content": "Explain gravity in one sentence."})
result = pipe.generate(
    history,
    max_new_tokens=64,
    streamer=lambda text: print(text, end="", flush=True),
)
history.append({"role": "assistant", "content": result.texts[0]})
history.append({"role": "user", "content": "Now give an example."})
print(pipe.generate(history, max_new_tokens=64))
```

Chat requires a suitable template in the GGUF metadata. See [Tokenization](./tokenization.mdx) for configuring the tokenizer and [Streaming](./streaming.mdx) for streamer behavior.

## Multi-token prediction (MTP)

Some GGUF checkpoints store NextN draft blocks after the target layers
(`<arch>.nextn_predict_layers`). GGUF MTP drafts are supported by the
`ContinuousBatchingPipeline` with the matching converted VLM target that provides a text embeddings model
(`openvino_text_embeddings_model.xml`). Pass the VLM directory as the main model and the GGUF
checkpoint as `draft_model_path`. The regular `LLMPipeline` and a raw GGUF main model are not
supported for GGUF MTP.

<LanguageTabs>
    <TabItemPython>
        ```python
        import openvino_genai as genai

        pipe = genai.ContinuousBatchingPipeline(
            "path/to/converted-vlm", genai.SchedulerConfig(), "CPU",
            {"draft_model_path": "model-with-mtp.gguf", "GGUF_READER": "FRONTEND"},
        )
        config = genai.GenerationConfig(max_new_tokens=64)
        print(pipe.generate(["Explain speculative decoding."], [config])[0].m_generation_ids[0])
        ```
    </TabItemPython>
    <TabItemCpp>
        ```cpp
        #include <iostream>

        #include <openvino/genai/continuous_batching_pipeline.hpp>
        #include <openvino/genai/gguf.hpp>

        int main() {
            ov::genai::ContinuousBatchingPipeline pipe(
                "path/to/converted-vlm", ov::genai::SchedulerConfig{}, "CPU",
                {ov::genai::draft_model_path("model-with-mtp.gguf"), ov::genai::gguf_reader("FRONTEND")});
            ov::genai::GenerationConfig config;
            config.max_new_tokens = 64;
            const auto results = pipe.generate(std::vector<std::string>{"Explain speculative decoding."}, {config});
            std::cout << results[0].m_generation_ids[0];
        }
        ```
    </TabItemCpp>
</LanguageTabs>

`draft_model_path` may point to a GGUF file with MTP layers or an OpenVINO IR directory.
The GGUF draft is compiled with the target device and properties.

The GGUF frontend currently builds drafts for `qwen35` checkpoints with one NextN block that
shares the target token embeddings, such as PrismML's
`Ternary-Bonsai-2-4B-PQ2_0-MTP-Q8_0.gguf` and `Ternary-Bonsai-2-9B-PQ2_0-MTP-Q8_0.gguf`.
GGUF files without NextN weights cannot be used as MTP drafts.
For M-RoPE MTP targets, provide text prompts; pre-tokenized token-ID inputs are not supported.

GGUF MTP uses paged attention and supports greedy or multinomial decoding, one returned sequence
and a fixed positive `num_assistant_tokens`; an unset value means 3. Confidence-based drafting and
tree search are not supported. With prefix caching enabled for a model with linear-attention state,
decoding must be greedy. A one-token prompt runs without drafting because the shifted draft context
is empty.
Recurrent-state capacity must cover both live requests and MTP verification scratch. With a custom
`scheduler_config`, set `num_linear_attention_blocks` to at least the number of live requests plus
`num_assistant_tokens + 1`, and add one more block when prefix caching is enabled. The legacy reader and
`enable_save_ov_model` are not supported for GGUF MTP drafts and raise an error. MTP acceptance
and speed depend on the checkpoint, prompt and hardware; enabling it does not guarantee a speedup.
